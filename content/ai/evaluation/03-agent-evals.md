Workflow 的评测是函数测试（输入 → 断言输出），Agent 的评测难在**输出是整条轨迹**：调了哪些工具、参数对不对、顺序合不合理、何时停止、每步如何自愈。最终答案正确不代表过程健康（可能只是碰巧对了），答案错误也不代表决策全错。Agent evals 的核心问题是：**评什么、谁来评、权重怎么定**。

## 三个评测层

**1. 结果层（end-to-end）**：最终答案/任务产出对不对。必测，但不够——它无法定位失败环节。

**2. 轨迹层（trajectory）**：过程对不对。按维度拆：

| 维度 | 问的问题 | 怎么判 |
|---|---|---|
| 工具选择 | 该用的工具用了吗、不该用的乱用了吗 | 轨迹里工具序列 vs 期望集合 |
| 参数质量 | 检索 query 质量是否合格 | judge 或规则（长度/关键词覆盖） |
| 效率 | 几轮收敛？重复调用几次 | 程序统计（轮数、token、重复检测） |
| 自愈 | 出错后修正了吗 | 构造"第一步必然失败"的用例，看恢复 |

**3. 单步层（step-level）**：给定这条上下文，这一步的决策对吗？——把轨迹切成"到达该步的状态 → 实际决策"，让模型/人评单个决策。最精细也最贵，用于深挖特定失败模式。

## 构造评测集：给轨迹出题

轨迹评测的用例设计比 RAG 更讲究，要**故意设计难度曲线**：

- **干扰项用例**：库里塞近似但不相关的文档，看 Agent 是否被干扰
- **必然失败用例**：第一个工具必然报错，测自愈（错误反馈 → 修正重试，见[最小循环](../agent/03-minimal-agent-loop.md)）
- **拒答用例**：任务无解（工具不可能返回所需信息），期望 Agent 明确表示做不到而不是编造
- **多跳用例**：必须按顺序查 A→B→C 才能答，测规划
- **预算用例**：给严格轮数/成本上限，测"在约束内尽量好"

每个用例记录**期望的轨迹特征**（必须用到的工具、最大轮数、禁用的工具），不只记录期望答案。

## LLM-as-judge 的坑（Agent 场景加倍）

[上一篇](02-ragas.md)说过 judge 有噪声，Agent 场景再加三条：

- **轨迹膨胀偏置**：judge 倾向给"步骤多、显得努力"的轨迹高分。先跑效率指标（程序可算），judge 只评质量问题
- **结果偏置**：答案正确时 judge 会无视过程中的危险操作（多余写库、越权尝试）。**危险操作检查必须是规则判定**，不交给 judge
- **自评偏置**：用同一模型既当 Agent 又当 judge，打分会对自己的风格偏好更宽容。judge 换模型，或至少换 prompt 视角

工程解法是**混合裁判**：能写规则的绝不 judge（工具序列、轮数、成本），judge 只负责语义类维度（理由是否充分），所有 judge 结论抽样人工校准。

## 指标权重：防止优化目标错位

结果、轨迹、效率、成本，多目标必然有权重。两条纪律：

- **权重按业务定**：客服场景拒答率权重最高；研究场景结果质量最高；无人值守场景优先约束成本与失败率
- **警惕 Goodhart**：把"轮数少"设成硬指标，Agent 会学出提前放弃的策略。效率类指标设下限约束（必须尝试 ≥ N 次不同策略），不要设"越少越好"的梯度
