多智能体（multi-agent）是最容易被高估的模式：多个 LLM 角色互相协作，听起来很吸引人。工程现实是：**每加一个 Agent，就加一份上下文不一致、一份级联失败、一份调试成本**。下文先说明为什么多数情况不该用，再讲确实要做时的架构选择。

## 什么问题真的需要多个 Agent

单 Agent + 多工具不够用的三个真实信号：

1. **上下文互相污染**：一个 Agent 的工作记忆装不下所有子任务。研究型任务（检索、分析、写作各自要不同的大上下文）拆给独立上下文的 Agent 才干净
2. **视角/权限必须隔离**：评审者不共享实现者的推理上下文；工具权限按角色收窄（写数据库的 Agent 不该能发邮件）
3. **并行吞吐**：多个独立子任务天然可并行，单 Agent 串行太慢（配合[并行化模式](02-five-patterns.md)）

**反过来，下面这些不是理由**：想模拟"公司组织架构"、觉得"多个 Agent 讨论会更聪明"（多数时候只是多花几倍 token 得到同样的结论）、框架教程演示里的 agent 团队。

## 三种主流拓扑

**1. 编排者-执行者（orchestrator-worker）**：一个编排 Agent 拆任务、派发、汇总（[模式四](02-five-patterns.md)的 Agent 版）。编排者持有全局状态，worker 各自独立上下文。**默认首选**：全局视角集中在一处，调试时看编排者的决策轨迹就能定位大部分问题。

**2. 流水线（pipeline）**：A 的输出是 B 的输入，顺序固定。如果流程固定，它就该写成 workflow 而不是"多 Agent"，这常是伪需求。

**3. 辩论/群聊（debate / group chat）**：多 Agent 互相讨论达成共识。研究价值 > 生产价值；生产里最多用于"生成后多视角评审"，且评审结果聚合用程序逻辑而不是让它们聊到收敛。

## 工程纪律：多 Agent 系统的稳定条款

- **接口即合同**：Agent 之间的传递用结构化 schema（pydantic），不是自由文本；自由文本传递等于把误解写进系统
- **每个 Agent 单一职责 + 独立可测**：拆出来的每个 Agent 单独跑[评测](../evaluation/03-agent-evals.md)，整体质量的上限是每个部件的质量
- **编排者掌握状态**：全局进度、已完成结论放在编排者的状态对象里（参考[记忆与状态](04-memory-and-state.md)），worker 只拿到"完成你的活所需的最小上下文"
- **轮数与预算上限**：多 Agent 的成本失控是乘法级的（worker 数 × 轮数 × token），每层都要有界

## 一个诚实的迁移路径

1. 先写**单 Agent 版本**（哪怕丑），建评测集
2. 评测失败案例里，能归因到"上下文装不下"或"权限要隔离"的，才值得拆
3. 拆的时候先拆**编排者-执行者**，worker 数量从 2 开始
4. 每拆一次跑一次整体评测；质量没有提升的拆分就是纯增加成本的拆分
