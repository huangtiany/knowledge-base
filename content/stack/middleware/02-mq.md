前端的事件总线（EventBus / mitt）用于组件间解耦通信；**MQ（消息队列）** 是它的服务端放大版——但价值远不止"解耦"，它是高并发系统的三大件之一（缓存、MQ、分库分表）。

## 为什么需要 MQ：三个场景

**1. 削峰（最有价值）**：秒杀活动 10 万请求瞬间涌入，MySQL 撑住 2000。把下单请求写进 MQ 就快速返回"排队中"，后端按自己的节奏消费——**流量洪峰被 MQ 水库蓄住了**。对照前端：UI 线程处理不了的事件排队进任务队列，慢慢消化。

**2. 解耦**：下单后要通知库存、积分、短信三个系统。同步调用 = 订单服务依赖三家的接口稳定性（任何一家挂了下单就失败）；改成发一条"订单已创建"消息到 MQ，谁需要谁订阅——**订单服务不再认识任何下游**。

**3. 异步**：下单主流程只需要落库，短信/积分都慢（几百 ms）；同步做 = 用户等三者之和。发 MQ 后立即返回，耗时的活交给消费者后台干。对照前端：把串行 await 改成 fire-and-forget，但 MQ 保证"没做的任务不会丢"。

## RabbitMQ 核心模型

```text
生产者 → Exchange（交换机）→ 按规则路由 → Queue（队列）→ 消费者
```

- **生产者**只把消息发给 Exchange，**不直接碰队列**
- **Exchange** 按 routing key 把消息路由到一个或多个队列（direct 精确匹配、topic 通配匹配、fanout 广播——对照事件总线的 on('xxx') 匹配规则）
- **消费者**订阅 Queue，**手动确认（ack）**处理完成——没 ack 的消息会重新投递，这是"不丢"的机制基础

## Spring Boot 集成

```java title="rabbitmq.java"
// 生产者：发消息
rabbitTemplate.convertAndSend("order.exchange", "order.created", orderDto);

// 消费者：监听队列
@RabbitListener(bindings = @QueueBinding(
        value = @Queue("point.queue"),
        exchange = @Exchange(value = "order.exchange", type = ExchangeTypes.TOPIC),
        key = "order.created"))
public void onOrderCreated(OrderDTO dto) {
    pointService.add(dto.getUserId(), dto.getAmount());   // 加积分
    // 方法正常返回 = 自动 ack；抛异常 = 消息重投（配合重试上限与死信队列）
}
```

对照前端的事件监听：`@RabbitListener` ≈ `eventBus.on('order.created', handler)`——差别是**跨进程、跨服务**，且消息有持久化与重投语义。

## 两条工程纪律

1. **消息别丢**：生产者确认（broker 收到回执）+ 消息持久化（Exchange/Queue/Message 都设 durable）+ 消费者手动 ack——三环缺一环都可能在故障时丢消息。反过来，**消息会重复**（重投机制），消费者必须**幂等**（同一消息处理两次结果不变，常用手段：业务唯一键判重）——"至少一次投递 + 幂等消费"是 MQ 的标准姿势
2. **入门即可，别过度设计**：学路线里 MQ 标注"项目中真实使用时再深入"——先把三价值 + 模型 + 幂等守住，具体选型（RabbitMQ/RocketMQ/Kafka）按公司技术栈来，概念是相通的
